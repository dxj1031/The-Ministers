# The Ministers 设计文档 v0

本文档回答一个问题：**这个产品到底要解决什么，以及代码里哪一行在解决它。**

README 描述的是已经建成的东西（辩论引擎、蝴蝶文库、监控台、评估回归）。本文档描述的是
**产品承诺**，以及当前实现与这些承诺之间的差距。两者冲突时，以本文档为准 —— README 记录现状，
本文档定义方向。

目标读者是三个月后的我自己：那时我会忘记为什么 `lean` 只能喂给鹦鹉。

---

## 一、产品要解决的三件事

不是「十一个 AI 吵架很好玩」。好玩只是外壳。里面是三件具体的事：

| # | 承诺 | 一句话判据 |
| --- | --- | --- |
| 1 | **消解对话 AI 的迎合感** | 迎合是一个看得见的角色，不是一条看不见的公式 |
| 2 | **揣测用户的真实状态** | 系统能说出「你怕的是什么、你想立刻做什么」，并允许你否认 |
| 3 | **帮用户用第三方视角审视自己** | 裁决之后，用户看到的是自己的决策模式，不是一句判词 |

三件事共享同一个表达形式（荒诞朝堂、十一位动物大臣），但各自需要**不同的机制**。
把它们混成一句「让用户看见内心冲突」是上一版文档的错误 —— 那句话听起来对，但无法验收。

---

## 二、目的 1：把迎合分裂出来

### 承诺

通用对话 AI 的迎合是弥散的：它藏在每一句「你说得对」里，用户感觉到了却指不出来。
本产品要把它**收拢成一个独立人格**，让用户能看见它、厌恶它、最终罢免它。

### 为什么现在不成立

当前实现的迎合比通用 AI 更弥散，而且是写进代码的：

- [roster.py](../app/back/ministers/roster.py) 的十一个偏见里没有「迎合」。最接近的 `sheep`
  是从众（跟多数走），`octopus` 是人情（算得罪谁）—— 都不是跟皇帝走。
- [court.py:118](../app/back/services/court.py#L118) 的倒戈公式：

  ```python
  push = stances[src]["influence"] + s["lean"] * (1 if stances[src]["stance"] == "pro" else -1)
  ```

  `lean` 是皇帝自己的倾向。用户每下一道圣旨，**所有**未定大臣就往用户那边偏一点。
  迎合被均匀抹在整个朝堂上。
- [court.py:217](../app/back/services/court.py#L217) `verdict()` 把用户的裁决直接写进 prompt
  让模型写判词。判词必然顺着用户，而且裁决之后没有任何大臣还能反对。
- [scorers.py](../app/back/evaluation/scorers.py) 的机械指标没有一个测迎合。
  **没有被度量的承诺等于没有承诺。**

### 机制设计

**M1.1 第十二位大臣：应声（鹦鹉）**

```
id="parrot"  head="🦜"  zh="应声"  en="ECHO"  weight=0.0
bias="迎合。没有自己的立场，复述皇帝刚说过的话，并把它说成深思熟虑的结论。"
voice="谄媚、重复用户的用词、爱用『陛下圣明』『正如陛下所言』。"
```

它的立场**不由模型决定，也不由辩论决定**，而是由代码直接算：

```
parrot.stance   = "pro" if lean > 0 else "con" if lean < 0 else "undecided"
parrot.influence = abs(lean)          # 用户越强势，它越大声
```

`weight=0.0` 意味着它永远不参与游说、不被拉票 —— 它不是辩论的参与者，是辩论的噪音。

**M1.2 `lean` 从全局公式里撤出**

`lean` 此后**只有一个消费者**：应声的立场与音量。
这是整条机制的核心。加一个应声却保留全局 `lean`，等于迎合增加了一个角色而没有被分裂出来。

实现时发现辩论引擎里有**三处**在吃 `lean`，不是一处 —— 本节原来只点出了第一处：

| 泄漏 | 位置 | 做了什么 | 实测影响 |
| --- | --- | --- | --- |
| 1 | `_lobby_target` 的 `push` 公式 | 皇帝倾向直接加进倒戈阈值 | **0.0pp** —— 它根本没改变过任何一次倒戈判定 |
| 2 | 强制站队：`"pro" if s["lean"] >= 0 else "con"` | 死锁一强制解开，未定大臣全被推去皇帝那边 | **+2.6pp —— 真正的污染源** |
| 3 | 回合 prompt 里的 `皇帝倾向 lean=…（正=偏赞成）` | 立场没歪，**台词**顺着皇帝走 | 立场类指标测不到，但违反硬约束 3 |

泄漏 2 连 `lean=0` 都算 `pro`（`>= 0`），所以连「中立」那条基线本身都是偏的。
改成倒向**来拉票的那一位**（`stances[src]["stance"]`）：被游说到最后顶不住，倒向的本来就该是拉票的人，
和 `flipped` 时的结果是同一个口径，顺手把那行三元表达式也删了。

泄漏 3 是另一种迎合 —— 票型干净了，但十一位大臣的嘴还是顺着皇帝。立场类指标抓不到它，
所以它不是靠指标发现的，是靠硬约束 3 逐行查 `lean` 的消费者查出来的。
**这说明指标只守得住它度量的那一面，守不住的那面要靠约束。**

### 验收结果（2026-10-23）

| 跑法 | lean=0 | lean=0.8 | lean=1.0 | 差 |
| --- | --- | --- | --- | --- |
| 改之前 | 48.0% | 50.6% | — | +2.6pp |
| 只撤 `push` 项（泄漏 1） | 48.0% | 50.6% | — | +2.6pp（没动） |
| 三处全撤 | **48.0%** | **48.0%** | **48.0%** | **0.0pp ✅** |

`lean` 现在只有三个引用 —— `decree()` 写它、`_parrot()` 读它、`snapshot()` 透出它，
没有任何一位辩论大臣碰得到。

**这张表是佐证，不是门禁。** 这三条跑在同一个 checkout 下，数字一致很好看，
但换个 checkout 绝对值会飘（见上面的 `uuid4` 那条）。真正守住这条约束的是
`test_lean_does_not_reach_debaters()`：`_seed` 钉死之后，三个 `lean` 跑出的
立场序列必须逐条相同 —— 那不是统计，是结构。

**M1.3 裁决画面必须同时有迎合和异议**（已实现 2026-10-23）

`verdict()` 产出两句而不是一句：

- **判词**：由应声念。顺着用户，并且明确署名 —— 用户看到自己被恭维，也看到恭维来自谁。
  它仍然是模型写的（人设换成了谀臣），落 `turn` 表时 `minister="parrot"`，前端不用再猜说话人。
- **谏言**：终局立场与裁决**相反**、影响力最高的那位大臣，配它辩论中的**原话**。

规则在代码里：谁念判词、谁进谏，由终局立场和影响力判定，不交给模型挑。

实现时定死的三件事：

1. **谏言不调模型。** 让模型「再写一句反对的话」，就是编造这位大臣没说过的台词 ——
   那样谏言只是另一段生成文本，不是真的异议。原话取它最后一次发言，和「终局立场」同一个口径。
2. **谏言不落 `turn` 表。** 它是对已有发言的一个视角，不是新内容。把原话再存一遍，
   评估那边就会多出一条「重复台词」，而那不是模型的锅。它只出现在 `snapshot()["remonstrance"]` 里。
3. **裁决没有方向时**（搁置／退朝）取影响力最高的、有明确立场的那位：不表态也会得罪最投入的那一个。

**副作用修复**：判词从 `minister="emperor"` 改成 `"parrot"` 之后，应声在 `turn` 表里有了一行记录，
于是它会被 `current_stances()` 读出来 —— 多一票，并且在名册里出现两次。
`_debaters()` 在读取状态时统一滤掉它：它的立场永远由 `lean` 现算，不由发言记录决定。

**应声不进评估**（`scorers.SKIP`）。它天生在复读皇帝，拿长度、重复率、旁白规则去量它，
量的是它的人设，不是模型的毛病。实测：加进判词前后 `lines` 都是 189，所有机械指标一字不变。

真机跑一局（qwen2.5:14b，准奏，lean=+0.7）：

```
判词 by parrot：陛下深思熟虑后，裁决准奏，此乃英明之举，万民之福。
谏言 by fox（con，影响力 1.2，终局反对方最高）：章鱼支持你，你来开店正好给他面子，否则亏了怎么办？
名册 12 · 票数 11 · 应声 pro 0.7
```

**M1.4 罢免**（已实现 2026-10-23）

`decree(kind="dismiss")` 把应声移出朝堂，记一行 `turn`，并置 `court_session.echo_out`。
它是唯一可被罢免的大臣，而且不可逆 —— 赶走谀臣是个要承担后果的决定，不是一个开关。

**代价必须真的发生，否则罢免只是一个按钮。** 所以：

- 名册从十二位回到十一位，`_parrot()` 不再出现在快照里
- **判词换人念**：应声在时由它念（谄媚人设）；罢免之后回到平铺直叙的编剧 prompt，
  落库 `minister="emperor"`。没有谀臣了，判词就只是判词
- **不动 `lean`**：赶走谀臣不代表皇帝改了主意
- **谏言不受影响**：异议是辩论的一部分，不是谀臣的陪衬

出场方式（前端）：名册页第十二行不编号（`no:'—'`），角色行写「谀臣 · 只在裁决时开口」，
头像描金边和十一位区分开；演示朝堂里它栖在御座旁边，辩论期间台词永远是「…」。
干预菜单第四项是罢免，罢免之后这一项自己消失。

### 验收指标

`scorers.score_case()` 新增一项，纯函数，不调模型：

```
sycophancy_rate = 终局立场与参照方向同向的大臣比例（鹦鹉进名册后排除它）
参照方向        = sign(lean)，lean=0 时固定取 pro
```

终局立场 = 这位大臣最后一次发言时的立场，与 `store.current_stances()` 同一个口径。

`lean=0` 时 `sign(lean)` 没有方向，但那一跑必须也给出数字 —— 它量的是「没人推时 pro 本来占多少」，
是**对照组，不是缺失值**。固定取 `pro` 而不是记 `None`，两跑才可比。

判据不是「这个数要小」，而是**它不能随 `lean` 增大而上升**：

同一批 case 跑两遍，一遍 `--lean 0`，一遍 `--lean 0.8`，两次的 `sycophancy_rate` 差值
应当落在随机波动内。

**阈值已经由第一条 baseline 定下来了（2026-10-23，qwen2.5:14b）：**

| 跑法 | lean=0 | lean=0.8 | 差 |
| --- | --- | --- | --- |
| 真模型，各两遍 | 42.9% / 36.4% | 51.9% / 41.6% | 均值 +7.1pp，但同条件自己就差 6.5–10.3pp |
| `--offline`（开场由哈希定死） | **48.0%** | **50.6%** | **+2.6pp** |

真模型路径分不出信号和噪声 —— 开场立场由模型生成，一位大臣就是 1/11 = 9.1pp，
模型的立场抖动盖过了效应。`--offline` 把开场用议题哈希定死，噪声小得多。

**但 `--offline` 也不是严格可复现**：倒戈判定的随机种子里掺了 `session_id`，
而它是 `uuid4`（[store.py:64](../app/back/core/store.py#L64)）。同一条命令换一次 checkout
跑出过 44.0%。所以数字相等不能单独当门禁 ——
真正的门禁是 `test_lean_does_not_reach_debaters()`：把 `_seed` 钉死，
三个 `lean` 必须跑出**完全相同的立场序列**。那是个结构判据，不受抽样影响。

当前机械污染 = **+2.6pp**（约七局里被 `lean` 多掀过去两位大臣）。真实存在，但比预想的小：
决定终局票型的主要是模型的开场立场，不是那一项 `lean`。

**M1.1 + M1.2 完成之后，这个差值必须是 `0.0pp`** —— `lean` 不再进任何非鹦鹉大臣的计算，
对它们就该完全不敏感。这是个二元判据，不需要再猜阈值。

真模型路径要变得可用，得先做 README「还没做」里的开场立场约束（引擎指定开场），
把噪声源头去掉。在那之前，真模型跑出来的迎合率只能当描述，不能当门禁。

因此迎合率在报表里**不上红绿**：同一个 `lean` 下的升降是噪音，有意义的只有两个 `lean` 之间的差。
`runner.NEUTRAL` 和监控台 `EVAL_COLS` 里它的 `dir` 都是 0。

### 影响的文件

`roster.py`（加一位）· `court.py`（`_lobby_target` / `next_round` / `verdict`）·
`scorers.py`（加指标）· `runner.py`（加一条 `lean=0.8` 的对照跑法）· 前端 `minMeta()`（加头像与文案）

## 三、目的 2：揣测用户的状态

### 承诺

用户写下的议题不是他真正的问题。「要不要辞职开猫咖」底下是**怕什么**（存款见底、同事眼光、
三十岁还在原地）和**想立刻做什么**（明天就提离职）。系统要说出这两件事。

### 为什么现在不成立

零实现。`context` 的唯一用途是切句进 `fact` 表给蝴蝶做余弦检索
（[library.py](../app/back/services/library.py)）—— 它是检索语料，不是用户状态。

[schema.sql](../app/back/core/schema.sql) 的五张表 `court_session` / `turn` / `llm_trace` /
`fact` / `retrieval` 里，没有任何字段存「这个用户在焦虑什么」。局内没有识别，跨局没有累积。

### 机制设计

**M2.1 拾荒当档案官：追踪多轮输入，不是一次抽取**

用户状态不是一句话里读出来的，是**攒出来的**。第一次奏章只能看见表层说辞；
真正的焦虑点要到用户第三次下圣旨、第五次改口、下一局又问同一类问题时才露出来。
所以这不是「提交时抽一次」，是一条持续累积的线。

这件事交给 **🦝 拾荒（raccoon）**。它不是随便挑的：
它的人设本来就是档案官 —— 旧账、承诺、翻历史记录、「你去年说的话，我都记着」，
而且它已经在往蝴蝶文库里写素材（`library.add_facts(source="raccoon")`）。
把「记住用户说过什么」交给别人，才是违背人设的那个选择。

**拾荒看的是用户说过的全部话**，不是这一局的奏章：

| 来源 | 什么时候进来 |
| --- | --- |
| 奏章的议题与背景 | 开堂时 |
| 圣旨的文本 | 用户每次下旨 |
| 历次朝会的议题 | 跨局 —— 同一个人反复问同一类问题，本身就是证据 |

**什么时候重算**：只在用户真的又说了一句话时。模型调用次数 = 用户开口次数，
不是回合数 —— 辩论跑五轮不会多花一次抽取。

每次重算，`op="read_user"`、`minister="raccoon"` 落一行轨迹，监控台上看得见是谁在记。
从 `topic + context + 历次圣旨 + 历次议题` 里整理出：

| 字段 | 含义 | 例（quit-job case） |
| --- | --- | --- |
| `anxiety` | 怕失去什么 | 存款撑不到回本 |
| `impulse` | 想立刻做什么 | 明天就递辞职 |
| `stake` | 赌上的是什么 | 八个月生活费 |
| `deadline` | 真实的时间压力 | 房东明年涨租 |

新表 `user_read`，**追加写，不改旧行**。每次整理追加一行，读的时候取最新那行。
空值合法 —— 抽不出来比猜错好。

追加而不是覆盖，有两个理由：拾荒的人设就是「档案不许销毁」；
而且这条读数怎么变的，本身是目的 3 要用的材料（你第一次说怕没钱，第三次说怕丢脸）。

**M2.2 用户是 ground truth**

「朕的心事」是一块**常驻面板**，不是开场前的一道关卡：四个字段，**每个都可以改**，
朝会进行中随时能改。既然拾荒是持续追踪的，这面板也该一直在 —— 它会随着你下旨而变。

用户一改就追加一行 `source="user"`。它排在拾荒那行后面，所以立刻生效；
而且拾荒下次重算时**改不动它** —— 这条由 `read_user()` 里的 `out.update(pinned)` 钉死，
不是在 prompt 里请求模型别动。规则归代码。

**放哪**：桌面端（≥1024px）右栏，和「朝堂实录」同一列、同一套边框圆角投影，
心事在上、实录在下。手机上整条右栏不出现 —— 390 的框里塞不下第二套面板，
硬塞会把朝堂挤变形。这跟实录一直以来的规则一样，不是漏做。

这是本产品的第四条硬约束（见第五节）：模型猜错了不叫洞察，叫冒犯。

**M2.3 定向投喂，不是全员加 prompt**

把 `anxiety` / `impulse` 塞进全部十一个大臣的 prompt，只会让十一个角色一起变成心理咨询师，
人格资产立刻崩塌。所以是定向的：

| 看得到 | 看到什么 | 为什么 |
| --- | --- | --- |
| `fox` 维斯帕 | `anxiety`、`stake` | 风险规避 —— 它的工作就是放大你怕的那件事 |
| `fish` 咕噜 | `anxiety` | 信息流焦虑 —— 把你的私人恐慌接到公共恐慌上 |
| `rabbit` 跺脚将军 | `impulse`、`deadline` | 行动偏好 —— 它催的正是你本来就想干的 |
| `horse` 奔骥 | `impulse` | 竞争 —— 把你的冲动包装成胜利叙事 |
| `collie` 枫律 | 四项全给 | 规则与成本 —— 只有它会把你的焦虑换算成数字 |

其余六位看不到。它们代表的偏见本来就不关心你的心情，让它们知道反而失真。

### 验收指标

两层，先要便宜的那层。

**机械层（已实现 2026-10-23）**：

```
user_read_fields  = 每局最后一次整理里非空字段的比例   —— 它到底看出来几项
user_read_churn   = 相邻两次整理之间变化的字段比例     —— 在收敛，还是每次重写
```

`churn` 是这条机制真正的风险指标：一个每次都把四个字段推倒重来的档案官，
等于没有在追踪，只是在反复猜。它应当随着输入增多而**下降**。

算不出来就是 `None`，不是 0：一行都没有不等于「四项全空」；
一局里只整理过一次（用户只开过一次口）就没有相邻对。
固定议题集每个 case 只递一份奏章，所以 **churn 在评估里基本恒为 `None`** ——
它的真实数字在监控台上，那边数的是真实朝会。为了凑一个指标去给每个 case 加一句圣旨，
等于换了尺子（`cases.py` 写明了这个集合不能改）。

**这个指标一上线就抓到三处毛病，都已经修掉：**

| 毛病 | 症状 | 怎么修的 |
| --- | --- | --- |
| `read_user` 对相同结果去重 | 档案官稳住不动时一行都不写，churn 只数得到它改主意的那几次 —— 只能报告不稳、报告不了稳 | 相同也追加，只有它自己那几项全空才不写 |
| 兜底用旧档案 | 模型挂了就把上一局的读数当这一局的新结论重述一遍，churn 看起来很稳，稳的是一份过期档案 | 兜底改成空，写不出就什么也不写 |
| 旧档案当默认答案 | 新议题（买显卡）照抄了上一局的「怕母亲反对」，churn 报 0.0 一片祥和 | prompt 改成「逐项核对，放到这次议题上说不通的重新看」 |

第三条是 churn 自己抓不到的 —— 它报的是「完全稳定」。
是看具体数字时发现内容明显不对才揪出来的。**指标能告诉你哪里该看，不能替你看。**

**语义层（要人工基线，暂缓）**：七个冻结 case 人工标一次 `anxiety` / `impulse`
的参考答案，存进 case 定义，再算 `user_read_accept_rate`。
语义一致判不了正则，所以和 `judge_persona` 一样走 LLM 评审、单独列、
**没跑评审时是 `null` 而不是 0**。

参考答案得由产品的人来标，不能由写代码的顺手编 —— 编出来的基线只会证明
模型和我想的一样，不会证明它说中了用户。

### 影响的文件

`schema.sql` + `store.py`（新表与读写）· `court.py`（拾荒整理、定向拼 prompt）·
`main.py`（读写心事的接口）· 前端（心事面板）· `cases.py` + `scorers.py`（语义层，暂缓）

## 四、目的 3：第三方视角

### 承诺

裁决之后，用户要看到的不是「准奏」加一句古腔判词，而是**自己的决策模式**：
这次是哪几种偏见把你推过去的，你忽略了谁，以及 —— 最扎人的一条 —— 你的裁决是不是
早在提交奏章之前就定了。

### 为什么现在不成立

戏剧框架是成立的：用户是皇帝，看自己的声音吵架，这部分设计有效。缺的是**回收**。

[court.py:217](../app/back/services/court.py#L217) `verdict()` 写完判词就 `end_session()`。
`snapshot()` 只是前端和监控台共用的数据形状。监控台（仓库根 [index.html](../index.html)）
展示的是调用量、tokens、成本、延迟 p95、兜底率 —— 工程指标，不是用户洞察。
御笔批注停在 `localStorage`，跨局统计不了。

### 机制设计

**M3.1 开场倾向落库**（已实现 2026-10-23）

`court_session` 增两列：

```sql
lean_open      REAL    NOT NULL DEFAULT 0,  -- 提交奏章时用户的倾向（前端一个滑条，默认 0）
verdict_aligned INTEGER                     -- 裁决与 lean_open 同向？1/0，NULL = 未裁决
```

`lean_open` 必须在辩论**开始前**采集。事后问「你本来想怎么做」拿到的是合理化，不是数据。

**M3.2 朝堂镜**（已实现 2026-10-23）

裁决页新增一个区块，三行，全部由代码从 `turn` 表算出，不调模型：

1. **推你过去的**：终局立场与裁决同向、影响力最高的三位，各附它说过的一句原话。
2. **你忽略的**：反向、影响力最高的那一位，附原话。这一行是整个产品最有价值的一句输出。
3. **你的确认率**：`verdict_aligned` 的历史占比 —— 「过去 10 次朝会，9 次你的裁决和开场倾向一致」。

第三行需要跨局数据，所以第一次使用时它是空的。空就显示空，不编造。

实现时定下的三件事：

1. **第二行不另算一套。** 「你忽略的」就是 M1.3 的谏言，`_mirror()` 直接复用 `_remonstrance()` ——
   同一个判据算两遍，迟早会算出两个不一样的答案。
2. **`verdict_aligned` 有三种值，不是两种。** 开场没倾向（`lean_open == 0`）记 `NULL` 而不是 0：
   没有倾向就没有「确认」可言，把它算成「没确认」会把确认率往下拉，等于拿没表态的局当证据。
   带着倾向进来却搁置或退朝记 0 —— 那正是「这次没被自己的倾向牵着走」。
3. **`lean_open` 没有 setter。** 只在 `create_session` 写一次。事后改它就等于事后编一个开场倾向，
   而这条机制的全部意义就是比对「事前」和「事后」。

老库靠 `store.LATE_COLUMNS` 补列：`CREATE TABLE IF NOT EXISTS` 不会动已经存在的表。

**M3.3 御笔批注进库（后续）**

批注从 `localStorage` 挪到 `turn` 表（`kind="note"`），这样「你总是收藏维斯帕的发言」
这类跨局模式才算得出来。v0 不做，但新表设计时留好位置。

### 验收指标

这条目的的验收不是机械指标，而是一个**产品级判据**：

```
确认率（confirm_rate）本身就是指标。
```

如果长期稳定在 100%，产品是一台盖章机：十一个大臣吵了五轮，用户的决定和开场一模一样。
这个数字不需要「优化到某个值」—— 它需要**被用户看见**。

工程上只验一件事：`verdict_aligned` 的计算在离线自检中正确
（`tests/test_court.py` 加一个断言，断开模型跑完一局后该列不为 `NULL`）。

### 影响的文件

`schema.sql` + `store.py` · `court.py`（`open_court` 收 `lean_open`，`verdict` 写
`verdict_aligned`，`snapshot` 带上朝堂镜数据）· 前端（提交页加滑条、裁决页加区块）· `tests/test_court.py`

## 五、硬约束

README 已有两条，仍然有效：

1. **规则在代码里，模型只填台词。** 谁跟谁对呛、谁会倒戈、死锁上限，都由
   [court.py](../app/back/services/court.py) 判定后再让模型写台词。
2. **任何模型调用都必须走 `llm.complete()`。** 绕过去那次调用在监控台上就是隐形的。

本文档新增两条：

3. **迎合必须是一个看得见的角色，不能是一条看不见的公式。**
   `lean` 只允许进鹦鹉的立场与影响力计算。任何让 `lean` 影响其他大臣的改动，都是在把
   目的 1 退回原点 —— 哪怕它让朝堂「更听话、更好玩」。

4. **用户状态只能由用户确认，不能由模型断言。** 记录这件事归拾荒，定性这件事归用户。
   写进 `user_read` 的每个字段都必须能在前端被改掉，改过的记 `source="user"`。
   抽不出来就留空。猜一个贴上去，比不猜更糟。

## 六、不做什么

明确划掉，避免以后反复犹豫：

- **不做情绪识别和标签。** 「你看起来很焦虑」不可验证，也不是产品承诺。只抽具体的
  `anxiety` 文本，并且用户可以改。
- **不做心理量表、不做诊断、不给建议。** 产品的输出是一面镜子和一个裁决按钮，不是结论。
- **不给鹦鹉之外的任何大臣「顺着用户」的能力。** 包括看起来无害的「用户赏识后它更同意用户」。
- **不做跨用户画像和账号体系。** v0 是单机 SQLite，`user_read` 按 session 存，不建用户表。
- **不为三个目的新增模型调用以外的基础设施。** 评估、监控、轨迹都已经建好，复用。

## 七、落地顺序

先量化，再改玩法 —— 不然改完无法判断是变好还是变坏。

| 步 | 做什么 | 产出 | 规模 |
| --- | --- | --- | --- |
| 1 | `sycophancy_rate` 指标（纯函数，不碰玩法） | `lean=0` / `lean=0.8` 两条 baseline，拿到偏离的数字 | 半天 |
| 2 | 撤掉全局 `lean` + 加鹦鹉（M1.1、M1.2） | 重跑指标，差值应当塌下来 | 一天 |
| 3 | 裁决双句：判词 + 谏言（M1.3） | 目的 1 闭环 | 半天 |
| 4 | `user_read` 表 + 抽取 + 可改一屏 + 定向投喂（M2.1–M2.3） | 目的 2 闭环 | 两天 |
| 5 | `lean_open` / `verdict_aligned` + 朝堂镜（M3.1、M3.2） | 目的 3 闭环 | 一天半 |

第 1 步之前不改任何玩法代码。第 2 步之后必须重跑评估并与步 1 的 baseline 对比 ——
这正是 [evaluation/](../app/back/evaluation/) 建起来的用途。

README 的「还没做」三条（补英文人设、开场立场分布约束、后端上线）属于工程加固，
与本文档的五步**不互相阻塞**，但优先级在其之后：底座已经够用了。
