# The Ministers

十一个带偏见的 LLM 智能体围绕一个问题吵架，用户扮演猫皇下最终裁决。

**线上**：[朝堂](https://dxj1031.github.io/personal-page/ministers/) · [监控台](https://dxj1031.github.io/personal-page/ministers/console.html)

> 线上是静态版：GitHub Pages 跑不了后端，所以朝堂走演示模式，监控台读一份本地真实跑出来的 `snapshot.json`。
> 想看真的辩论，按下面「运行」两行起来，模型可以是本地 Ollama。

工程上想解决的问题是：**十一个智能体同时说话，怎么保证它不是十一段随机文本**，以及**模型不可靠时产品怎么不崩、又不悄悄劣化**。答案是把规则放进代码、把每一次模型调用变成一行可查的记录 —— 见下面两条硬约束和监控台。

---

## 产品思路

`The Ministers` 是一个把“做决定”包装成荒诞朝堂喜剧的互动产品。用户扮演猫皇，把一个现实或脑洞议题写成“御前奏章”，十一位动物大臣会围绕这件事站队、争辩、互相游说，最后由用户下旨裁决。

当前 README 基于 [app/front/The Court.dc.html](app/front/The%20Court.dc.html) 的前端原型整理。该文件已经包含完整的单页体验、角色设定、辩论模拟、裁决流程和本地存储逻辑。

## 一句话定位

把用户脑中的不同声音外化成一场可观看、可干预、可裁决的多角色辩论。

它不是严肃的决策表格，也不是单一聊天机器人，而是一个“决策剧场”：用夸张角色和可视化冲突，让用户在娱乐中看见一个问题被风险、冲动、虚荣、规则、旧账、预兆、信息流、群体压力、确认偏误、奇思妙想和人情关系分别拉向哪里。

## 核心用户体验

1. **召集朝堂**
   - 开场以电影化动画进入朝堂氛围，建立“用户是皇帝、大臣为你争论”的戏剧框架。
   - 随后进入大臣名册，用户可以逐一认识角色、性格和招牌动作。

2. **提交奏章**
   - 用户输入今天要裁决的问题，例如“我要不要创业”“要不要辞职”“要不要先发消息”。
   - 可以补充背景，让大臣的立场更贴近具体情境。
   - 系统提供推荐议题和最近议题，降低启动成本。

3. **朝堂辩论**
   - 每位大臣获得初始立场：赞成、反对或未定。
   - 立场和影响力可由 `window.claude.complete` 生成；不可用时会走本地 fallback，保证原型可运行。
   - 大臣会移动、喊话、互相游说、发生冲突或触发特写事件。
   - 朝堂上方用天平和计时器表达当前支持/反对趋势。

4. **皇帝干预**
   - 用户可以暂停朝堂，点开大臣查看观点与理由。
   - 可以记录观点、赏识某位大臣、在冲突中站边，或直接发布圣旨影响朝堂风向。
   - 用户拥有最终裁决按钮：准奏、驳回、搁置、退朝。

5. **裁决与记忆**
   - 裁决后展示判词、议题和大臣反应。
   - 本地记录天数、最近议题、御笔批注、朝堂闹剧统计和中立历史。
   - 用户可以继续下一桩议题，也可以退朝后再次召集朝会。

## 角色系统

产品的主要趣味来自十一位动物大臣。它们不是随机头像，而是不同决策偏见和社会行为的拟人化：

| 角色 | 产品含义 |
| --- | --- |
| Lord Vesper，狐狸 | 谨慎、风险规避、永远预见灾难 |
| General Thump，兔子 | 行动优先、冲动执行、讨厌拖延 |
| Champion Gallop，马 | 竞争心、荣誉感、追求胜利叙事 |
| Sir Maple，牧羊犬 | 规则漏洞、成本优化、技术性绕路 |
| Archivist Trash，浣熊 | 旧账、承诺、记录和八卦 |
| Oracle Ssylith，蛇 | 神秘主义、预兆、模糊判断 |
| Glub the Doomscroller，鱼 | 信息流焦虑、网络恐慌、反复刷新 |
| Baa-ron Woolsey，羊 | 从众、共识、摇摆 |
| Curator Silk，蝴蝶 | 确认偏误、信息茧房、自证式资料库 |
| Jester Banana，香蕉 | 脑洞、随机灵感、半成品方案 |
| Chancellor Octavia，章鱼 | 人情管理、圆滑协调、关系优先 |

这些角色让产品拥有稳定的人格资产。用户不是在等模型“给答案”，而是在看一群可预期、可记忆、可偏爱的角色如何争论。

## 核心机制

- **立场与影响力**：每个大臣有 `stance` 和 `influence`，共同影响朝堂走势。
- **动态游说**：大臣之间会发生拉票、抵抗、转向，形成可视化的政治流动。
- **皇帝倾向**：用户的赏识、站边和圣旨会改变 `lean`，进而影响摇摆大臣。
- **辩论时限**：默认 45 秒辩论窗口，到时进入休庭/裁决阶段。
- **中立限制**：朝堂每 10 次最多死锁 2 次，避免产品总是停在“都可以”。
- **御笔批注**：用户可以保存某位大臣的观点，形成自己的决策记录。
- **朝堂记事**：统计摔碗、死谏、冲线、预兆、结茧等角色招牌行为，强化长期游玩感。
- **本地持久化**：通过 `localStorage` 保存天数、统计、议题历史、语言和设定。

## 辅助玩法

### 蝴蝶文库

`The Cocoon Library` 是一个迷你信息茧房系统：浣熊负责输入“事实”，蝴蝶负责把这些事实编织成看似自洽的结论。它不是为了提供客观检索，而是用玩法表达确认偏误：资料越多，不一定越接近真相，也可能越强化原本相信的东西。

### 召见大臣

用户可以单独和某位大臣聊天。当前实现会按角色人格拼接 prompt，优先调用 `window.claude.complete`，不可用时退回角色口头禅。这让角色从辩论棋子变成可对话的陪伴型角色资产。

## 产品价值

- **降低决策压力**：用户不需要一上来理性列优缺点，只要把问题交给朝堂。
- **让内心冲突具象化**：不同角色代表不同声音，冲突被展示出来，而不是藏在脑内。
- **兼具娱乐和反思**：荒诞表达降低严肃问题的心理负担，但裁决仍然推动用户形成结论。
- **天然适合复访**：每天都有新议题、角色统计、历史记录和可积累的朝堂记忆。
- **适合传播**：判决、角色反应和荒诞议题天然具备可截图、可分享的内容属性。

## 设计原则

- **戏剧优先**：界面不是工具外壳，而是朝堂本身。
- **角色先于模型**：AI 只负责增强具体议题反应，核心人格、规则和节奏由产品控制。
- **用户必须有权力**：用户不是旁观者，而是能暂停、记笔记、赏识、施压和最终裁决的皇帝。
- **答案不必绝对正确**：产品目标是帮助用户看清倾向、权衡冲突、做出一个更有参与感的决定。
- **轻量但可持续**：当前以单页原型和本地存储支撑完整闭环，后续可逐步接入后端、账号和分享体系。

## 还没做

- **蝴蝶文库接 RAG**：浣熊存事实 → embedding → 向量检索 → 蝴蝶只挑支持自己结论的片段，用检索命中率把「确认偏误」做成可量化的玩法。
- **评估回归集**：固定议题集 + 打分（人设不串台、立场分布、JSON 合法率、不出旁白），每次改 prompt 前后对比，结果进监控台。

## 后续方向

- 生成可分享的“圣旨判决卡”。
- 加强每位大臣围绕具体议题的长短论点生成。
- 增加议题包，例如职场、感情、消费、创业、家庭、奇葩朝政。
- 提供回放功能，让用户复盘一次朝会的关键转向。
- 把御笔批注沉淀成个人决策日志。
- 为角色增加成长、偏爱值或关系系统。
- 接入正式后端，保存跨设备历史、角色互动和公开议题榜。

## 运行

```bash
pip install -r requirements.txt
cp .env.example .env          # 默认指向本地 Ollama；没有模型也能跑，只是走角色口头禅兜底
python -m uvicorn app.back.main:app --reload --port 8010
```

- <http://localhost:8010/> — 监控台
- <http://localhost:8010/front/The%20Court.dc.html> — 朝堂
- 自检：`python tests/test_store.py` 和 `python tests/test_court.py`（强制断开模型，验证兜底路径能完整跑完一局）

### 两条硬约束

- **规则在代码里，模型只填台词。** 谁跟谁对呛、谁会被游说倒戈、死锁上限，都由 `court.py` 判定后再让模型写台词。换模型或模型胡说都不会让玩法崩掉。
- **任何模型调用都必须走 `llm.complete()`。** 绕过去直接发请求，那次调用在监控台上就是隐形的；模型挂掉时走兜底也会被标成 `fallback`，不会悄悄降级。
